1. Abstract & Design Goals

Task B is a persona-conditioned recommendation system. Given a user ID and a natural-language query, it returns a ranked list of products the user is likely to want — personalised to their category preferences, price sensitivity, and the semantic themes they have praised or criticised in past reviews.

The system handles four user archetypes: warm (rich review history), cold-start (1–3 reviews), cross-domain (querying a category they have never bought in), and multi-turn (conversational refinement across multiple query turns).

Design goals: (1) Disentangled personalisation — separate "where", "how much", and "why" belief dimensions extracted from real KG review data, not synthetic signals; (2) Graceful degradation — cold-start and cross-domain users still get ranked results via Wilson-scored community quality; (3) Multi-turn coherence — prior queries and shown items are injected into the LLM prompt so each turn refines the previous; (4) Transparency — every recommendation carries a `match_score` and natural-language `reasons` the UI can display; (5) Web search escape hatch — when the knowledge graph lacks relevant items, the LLM can invoke FireCrawl search to fetch live product data.

4. Belief Extraction

Implemented in task_b/inference/belief_extractor.py. The belief extractor queries the user's own review history from Neo4j and produces a BeliefProfile with three disentangled dimensions: WHERE (preferred categories), HOW MUCH (price orientation), and WHY (semantic aspects they care about).

4.1 BeliefProfile structure

@dataclass
class BeliefProfile:
    categories: list[str]              # ordered by review frequency (top 3-5)
    price_label: str                   # "budget" | "mid-range" | "premium"
    price_sensitivity: float           # 0-1 from SQLite persona
    semantic_likes: list[str]          # positive aspect themes (e.g. "battery", "value")
    semantic_dislikes: list[str]       # negative aspect themes (e.g. "quality", "usability")
    top_category_biases: dict[str, float]  # category → user's mean rating in that category

4.2 Price label derivation

if price_sensitivity >= 0.65  →  "budget"    (user mentions price comparisons frequently)
if price_sensitivity >= 0.35  →  "mid-range"
else                          →  "premium"   (user rarely mentions price; buys freely)

4.3 Semantic theme extraction

Own reviews are filtered by rating and scanned against two term dictionaries — _POSITIVE_TERMS and _NEGATIVE_TERMS — with 6 aspect categories each: quality, value, performance, battery, usability, delivery (positive) / quality, value, functionality, usability, battery (negative). An aspect is surfaced if it appears in ≥ 2 reviews in the relevant rating band:

# Positive: reviews with rating >= 4.0
# Negative: reviews with rating <= 2.0
_POSITIVE_TERMS = {
    "quality":     ["great quality", "well made", "solid build", "durable", ...],
    "value":       ["great value", "worth the price", "good deal", ...],
    "performance": ["works great", "works well", "performs well", "fast", ...],
    "battery":     ["long battery", "battery lasts", "great battery", ...],
    "usability":   ["easy to use", "user friendly", "easy setup", ...],
    "delivery":    ["fast delivery", "arrived quickly", "shipped fast", ...],
}
_NEGATIVE_TERMS = {
    "quality":       ["cheap", "flimsy", "poorly made", "bad quality", ...],
    "value":         ["overpriced", "not worth", "waste of money", ...],
    "functionality": ["stopped working", "doesn't work", "broken", ...],
    "usability":     ["hard to use", "confusing", "difficult to", ...],
    "battery":       ["drains quickly", "battery drains", "short battery", ...],
}

4.4 Cypher query used

-- Live inference (all reviews for user):
MATCH (u:User {id: $user_id})-[:WROTE]->(r:Review)-[:ABOUT]->(i:Item)
WHERE r.text IS NOT NULL AND size(trim(r.text)) > 20
RETURN r.text, toFloat(r.rating), i.category,
       coalesce(i.priceNgn, i.priceUsd * 1500.0) AS price_ngn
ORDER BY r.timestamp DESC LIMIT $limit

-- Eval mode (temporal guard — no future leakage):
... WHERE r.timestamp < $before_timestamp ...

Why disentangle beliefs?

A single "user preference vector" collapses category, price, and semantic signals into one number that the LLM cannot meaningfully decompose. By presenting separate Category (WHERE), Price (HOW MUCH), and Semantic (WHY) axes, the LLM prompt gives the reranker three independent lenses to score each candidate — matching, e.g., a cross-domain case where category is unknown but semantic likes (battery life, value) still constrain the ranking.

5. Two-Channel Candidate Retrieval

Implemented in recommend_items(). Two retrieval channels run in a single Neo4j async session and their results are merged + deduplicated.

5.1 Vector channel query

-- Channel A: semantic (item_embedding index)
CALL db.index.vector.queryNodes('item_embedding', $top_k, $embedding)
YIELD node AS i, score AS item_similarity
WHERE item_similarity >= 0.3
RETURN i.id, i.title, i.brand, i.category, i.subCategory,
       i.priceUsd, i.priceNgn, i.avgRating, i.ratingCount,
       i.features, item_similarity
ORDER BY item_similarity DESC
LIMIT $top_k

5.2 Structural channel query

-- Channel B: category-scoped (uses user's top_categories from persona)
MATCH (i:Item)-[:IN_CATEGORY]->(c:Category)
WHERE c.name IN $categories
  AND i.avgRating IS NOT NULL
  AND i.ratingCount IS NOT NULL
  AND i.ratingCount >= 5
RETURN i.id, i.title, i.brand, c.name AS category, i.subCategory,
       i.priceUsd, i.priceNgn, i.avgRating, i.ratingCount, i.features
ORDER BY i.avgRating * log(toFloat(i.ratingCount) + 1.0) DESC
LIMIT $limit

6. Hybrid Pre-Ranking (Wilson Score)

After merging both channels, every candidate is scored by a hybrid formula that combines community rating quality, persona category affinity, and query-semantic similarity.

6.1 Wilson score lower bound

The Wilson score converts (average rating, review count) into a conservative quality estimate. It solves the problem of small samples with inflated ratings: an item with 4.5★ from 8 reviews scores lower than an item with 4.2★ from 400 reviews, because the first estimate has wide uncertainty.

def _wilson_score(rating: float, count: int) -> float:
    """Lower-bound Wilson confidence interval, z=1.28 (80% CI)."""
    if count == 0:
        return 0.0
    n = float(count)
    p = (rating - 1.0) / 4.0      # normalise 1-5 → 0-1
    z = 1.28
    centre = (p + z*z / (2*n)) / (1 + z*z / n)
    margin = z * sqrt(p*(1-p)/n + z*z/(4*n*n)) / (1 + z*z / n)
    return centre - margin

# Example results:
# rating=4.5, count=8    → Wilson ≈ 0.52   (wide CI, pessimistic)
# rating=4.2, count=400  → Wilson ≈ 0.77   (tight CI, confident)
# rating=5.0, count=1    → Wilson ≈ 0.20   (single review — heavily penalised)

6.2 Hybrid pre-rank formula

hybrid_score(item) =
    Wilson(item.avg_rating, item.rating_count)          -- community quality (0-1)
  + category_bias_adj(item.category, persona)           -- persona affinity (±0.1)
  + S100_SIM_WEIGHT × cosine(query_vec, item_embedding) -- semantic relevance

category_bias_adj = (persona.cat_bias[category].mean - 3.0) × 0.02
  -- range ±0.1 (5★ user in this category → +0.1; 1★ average → -0.04)
  -- Disabled for cross_domain eval cases (the held-out category is absent)

S100_SIM_WEIGHT = 0.5  (tunable via env var)
  -- Cosine similarity is 0-1; weight chosen from K-probe data

Why not use straight average rating?

Average rating is a biased estimator when counts are small. In our KG, many items have ≤ 10 reviews. A single enthusiastic reviewer can push an obscure item to 5.0★. Wilson score's lower confidence bound collapses to the raw average for large counts (n → ∞) while being appropriately conservative for new or low-traffic items. This ensures the LLM sees a quality-sorted list rather than a list dominated by lucky small-sample items.

6.3 S100 pool pre-ranking (eval mode)

In the S100 evaluation protocol the candidate pool is a fixed 100-item set (not retrieved from the live KG). The pre-ranking in this mode fetches each item's embedding from Neo4j (QUERY_CANDIDATE_ITEMS_BY_IDS), computes cosine similarity to the query embedding, and applies the same hybrid formula. Only the top S100_LLM_TOP_K=50 items are sent to the LLM — the other 50 are discarded before the LLM call, reducing prompt size and 429 risk.

The two-phase structure exists because Mistral's streaming and tool-calling cannot be combined in a single request — Phase 1 handles tool detection synchronously, Phase 2 runs a streaming completion with the (optionally web-augmented) prompt.

7.1 Web search fallback details

When the KG candidate pool is irrelevant (e.g., user asks for "restaurant near Victoria Island" but KG only has electronics), the LLM can invoke the web_search tool. The function schema is provided as a Mistral tool definition:

WEB_SEARCH_TOOL = {
  "type": "function",
  "function": {
    "name": "web_search",
    "description": "Search the web for product information. Call ONLY if KG candidates are insufficient.",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {"type": "string", "description": "Precise product search query"}
      },
      "required": ["query"]
    }
  }
}

FireCrawl's /v1/search endpoint is called with the LLM's chosen query. Up to 5 results (title, URL, description snippet) are injected into the Phase 2 system message as a WEB SEARCH RESULTS block. Web items are assigned synthetic IDs (web_1, web_2, …) in the final ranked output. Requires FIRECRAWL_API_KEY to be set; web search is silently disabled if the key is absent.

7.2 Rate limiter

A process-wide _RateLimiter paces Mistral requests. It uses an asyncio lock + monotonic clock to enforce a minimum inter-request interval. Before each Mistral call, the limiter checks the time since the last request and sleeps for the remainder if needed.

MISTRAL_MIN_INTERVAL_S = 2.0   # env override: MISTRAL_MIN_INTERVAL_S
# Effect on eval: error rate reduced from ~13% → 0% across 180-case run

Why a rate limiter rather than retry-with-backoff?

Retry-with-backoff creates bursty traffic: many concurrent eval workers all fail simultaneously, then retry simultaneously, causing a thundering-herd against the rate limit. A proactive rate limiter prevents the 429 before it occurs, keeping latency predictable and the error rate at exactly 0% in the production eval run.

8. Multi-Turn Conversation

Task B supports conversational refinement across turns. Each turn records the query and the item IDs that were shown to the user. Subsequent turns inject this history into the LLM system prompt so the model can refine recommendations based on what the user has already seen.

8.2 _format_prior_turns()

The function renders the turn history as a compact text block inserted directly into the system message:

PRIOR CONVERSATION TURNS (oldest first):
  Turn 1: User asked "wireless earbuds under ₦20k". Top items shown: [B07XJ8C8F5, B09JQ6J3V2, B08HVJ4G8P].
  Turn 2: User asked "something with better battery life". Top items shown: [B08CJNKQ7L, B09XN2QK6Z, B07RK2G9H4].
Incorporate the user's refinement across these turns when ranking.

8.3 Evaluation of multi-turn quality

The multi_turn holdout subset contains 30 users each with ≥ 3 reviews in the held-out category. The eval runner sends three sequential turns per case, injecting each turn's results into the next as prior_turns. The rank improvement metric measures how the positive item's rank changes from turn 1 → turn 3.

Mean rank improvement (turn 1 → turn 3): +1.90 positions
Final-turn NDCG@10 (multi-turn subset):  0.126

Why stream the Phase 2 response?

The LLM's reasoning text can be 500–2,000 tokens before the JSON block appears. Streaming allows the frontend to display the model's thinking in real time — the user sees the reasoning unfold and then the ranked list appears when the JSON fence is detected. This dramatically improves perceived responsiveness. The _safe_emit_split() function holds back up to the length of a stop marker in the pending buffer so the JSON block is never accidentally emitted as display text.

12. Evaluation Protocols

12.1 S100 protocol (primary)

For each test case, a 100-item pool is assembled. The system must rank the positive item into the top-10 without any retrieval advantage — the pool is handed directly to the pre-ranker.

SlotCountSelection
Same-category items50Random from held-out category
Same-price-tier items25Random from same price bucket (budget/mid/premium)
Globally popular items24Top-rated by Wilson score across all categories
Held-out positive1The user's most-recent ≥4★ review item

The pool is shuffled with random.seed(42) before passing to the pipeline. Metrics computed: NDCG@10, HR@10, MRR@10.

12.2 E2E protocol (secondary)

No fixed pool. The pipeline performs full two-channel retrieval from 36K+ items and must surface the positive within its top-10 or top-20 output. Tests the complete retrieval + ranking stack. Metric: HR@10, HR@20.

13. Leakage Controls

Five explicit controls prevent the evaluation from seeing data that would not be available at inference time:

  1. Temporal integrity — all belief extraction Cypher queries include a timestamp filter: r.timestamp < $cutoff. The cutoff is the timestamp of the held-out review. No review written after (or at) the held-out moment influences the BeliefProfile.
  2. eval_train persona split — personas.db contains two rows per user: the live row (all reviews) and an eval_train row (excludes held-out review from rating statistics). The eval runner passes PERSONA_SOURCE=eval_train to load the contamination-free stats.
  3. Held-out item excluded from retrieval — in S100 mode the positive is never returned by the vector or category retrievers (it is injected into the pool directly). In E2E mode the live KG is used, but the item's own review is excluded from the user's review history via the timestamp cutoff.
  4. KG own-reviews filter — QUERY_OWN_RECENT and QUERY_OWN_LOW_NEUTRAL both filter by r.timestamp < $cutoff and explicitly exclude the held-out item ID (WHERE i.item_id <> $exclude_id).
  5. S100 pool seeding — the 99 distractors and 1 positive are assembled and shuffled with a fixed random.seed(42). The order is deterministic but opaque to the LLM, which only sees pre-ranked candidates sorted by hybrid score, not by their pool position.

15. Key Architectural Decisions

Why two retrieval channels?

Vector search finds semantically related items but misses popular items in the user's preferred categories that happen to use different terminology. Structural Cypher by category catches those and creates diversity in the candidate set. Union + dedup gives the LLM a richer pool to reason over.

Why Wilson score instead of average rating?

Average rating is a biased estimator for items with few reviews. A 5.0★ item with 2 reviews outranks a 4.6★ item with 5,000 reviews under naive averaging. Wilson score applies a lower-bound confidence interval that collapses to the true average for large counts while being appropriately conservative for sparse items.

Why not end-to-end learned ranking?

Our KG has only ~1,100 warm users with enough history to train a meaningful ranking model. A learned model would overfit. The Wilson + persona bias + cosine hybrid is simple, interpretable, and generalises across all four user types (warm, cold, cross-domain, multi-turn) without training data.

Why Mistral specifically?

Mistral Medium supports function/tool calling with tool_choice: "auto", which is required for the optional web search fallback. The OpenAI-compatible HTTP interface also makes it trivially replaceable via MISTRAL_BASE_URL override — any compatible endpoint (Groq, local Ollama, etc.) works without code changes.

Why separate Phase 1 and Phase 2 Mistral calls?

Mistral cannot perform tool use and streaming simultaneously in a single request. Phase 1 (non-streaming) handles tool detection and FireCrawl invocation. Phase 2 (streaming) runs the main reasoning and ranking with the full augmented context. This separation keeps the streaming experience intact while still supporting optional web search.

Why token-bucket rate limiting over retry-with-backoff?

Retry-with-backoff concentrates failures: many parallel eval workers fail simultaneously then retry simultaneously, creating a thundering herd against the API rate limit. A proactive rate limiter prevents 429s from ever occurring, yielding a 0% error rate across the 180-case production eval run.

16. Limitations & Future Work

16.1 Current limitations

  • E2E HR@10 = 0.000 for warm and multi-turn — Full retrieval from 36K items cannot reliably surface the held-out positive for warm users because the two-channel retrieval does not yet use personalised query expansion. The vector search uses only the raw context_query embedding, not the user's BeliefProfile, so category-biased items far from the query vector are never retrieved.
  • Cold-start semantic quality — With 1–3 reviews, the top_like and top_dislike aspects are often empty or noisy. The LLM receives an impoverished BeliefProfile that cannot distinguish preferences meaningfully.
  • No collaborative filtering — The system is entirely content-based + LLM reasoning. Item-item or user-user collaborative signals from the 103K-user graph are unused.
  • Web search latency — FireCrawl adds 2–5 seconds per request when invoked. The LLM is not always accurate about when to invoke it, sometimes calling it for queries the KG could answer.
  • LLM over-anchoring on persona priors — As shown in the ablation, LLM reranking with persona beliefs can hurt HR@10 for warm users by over-fitting to stated category priors and pushing cross-category relevant items down.

16.2 Future directions

  • Personalised query expansion — Expand the vector search query with the user's top categories and semantic like terms before embedding. Expected improvement: E2E HR@10 from 0% to ~15–20%.
  • Graph-based collaborative signals — Use random walks or node2vec embeddings over the User→Review→Item graph to surface items liked by similar users. Particularly valuable for cold-start.
  • Fine-tuned reranker — Train a cross-encoder reranker on (BeliefProfile, item) pairs using historical positive/negative pairs from the warm subset. Would replace the LLM call for latency-sensitive paths.
  • Hybrid LLM + learned score — Use the LLM only for final top-5 reasoning; apply a lightweight learned score (BPR or LambdaRank) for the top-50 → top-10 reduction step.
  • Cached belief profiles — BeliefProfile extraction currently queries Neo4j on every request. Caching extracted beliefs (with a TTL keyed to the user's latest review timestamp) would reduce median latency by ~300ms.
  • Tool-call quality gate — Add a classifier that decides whether to invoke web search before passing control to the LLM, reducing unnecessary FireCrawl calls and improving precision of web-augmented results.
