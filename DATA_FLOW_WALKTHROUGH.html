One Screen Summary

The stack is built around two persistent stores: Neo4j holds the review graph plus review and item embeddings; SQLite holds compact user personas and train-only eval personas. At runtime, the API takes a user and product, retrieves that user's style history plus exact-item or item-vector community evidence from the graph, builds two prompts, streams a review from an LLM, asks a second LLM call for a numeric rating, then applies deterministic calibration rules before returning the final simulated review.

1

Source Data

Amazon Reviews 2023, local Nigerian ecommerce JSONL, Nigerian Google Maps CSV.

2

Normalize

Every row becomes a ReviewRecord with user, item, rating, review text, metadata, price, locale, and platform.

3

Enrich

Compute stylometry and review embeddings using all-MiniLM-L6-v2 by default.

4

Persist

Write graph nodes/edges to Neo4j and user personas/category bias to SQLite.

5

Infer

Load persona, resolve item, retrieve style/content anchors, build prompts, call LLM twice.

6

Calibrate

Deterministic rating rules adjust obvious under/over predictions using persona and retrieved risk signals.

7

Evaluate

Hidden reviews are removed from Neo4j, stored in SQLite, generated against, and scored as held-out truth.

8

Visualize

The API emits graph_data over WebSocket; the UI renders Graph/Table/RAW tabs using Neo4j NVL.

Sampling

persona_friendly_sample() filters out rows missing user/item/review IDs, prioritizes users with at least three reviews, round-robins by category, then sorts deterministically by locale/platform/category/user/review. This matters because Task A needs repeated user histories, not just isolated one-off reviews.

Enrichment And Storage

Review Enrichment

  • word_count is computed from review text.
  • Stylometry is computed only when review length is above the minimum word threshold.
  • Review embeddings use sentence-transformers/all-MiniLM-L6-v2 by default, 384 dimensions.
  • Tests can use HashingEmbedder for deterministic fake embeddings.

Stylometry Features

  • Sentence length, vocabulary richness, average word length.
  • Exclamation, question, uppercase, emoji rates.
  • Pidgin token frequency.
  • Naira mention, price sensitivity, authenticity concern.

Neo4j Indexes

The writer creates standard indexes for user/item/review IDs, review locale, item category, parent ASIN, store, plus vector indexes named review_embedding on Review.embedding and item_embedding on Item.embedding, both using cosine similarity.

Current embedding scope: Reviews keep their existing embeddings, and products now also have Item.embedding. Item embeddings are generated from title, brand/store, category/sub-category, price bucket, features, description/details, source average rating, and rating count. This enables similar-product review retrieval before falling back to broad category evidence.

Inference Flow In Fine Detail

The central function is inference.task_a.simulate_review(). This is the production path, the WebSocket path, and the eval path.

  1. Receive SimulateRequest. Required fields are user_id, item_name, and price_ngn. Optional fields include exact item_id, product description, brand/category hints, USD price, raw message, and eval-only heldout_review_id.
  2. Build retrieval query text. _retrieval_query() concatenates raw_message, item_name, and item_description. This is used for LLM-Cypher retrieval, not directly as the final prompt.
  3. Load persona. load_persona() reads either production personas or eval eval_personas_train, controlled by PERSONA_SOURCE. It also loads category bias rows into persona["cat_bias"].
  4. Resolve item metadata. If item_id is provided, resolve_item() fetches the Neo4j Item. If not, resolve_item_by_title() tries title search. If neither works, request metadata becomes the fallback item record.
  5. Derive early user tendency. Before retrieval, the code classifies the user from rating_mean: generous if >= 4.3, balanced if >= 3.8, otherwise tough critic. This influences exact-item review filtering.
  6. Select retrieval branch label. Branch is category if category is known, query if query text exists, otherwise vector. The label is diagnostic; the retrieval function still has ordered tiers.
  7. Embed retrieval text. The system embeds item_name + category for review-vector fallback. It intentionally avoids embedding full spec text because product specs and review prose are semantically different.
  8. Fetch retrieval evidence. fetch_retrieval() returns own_reviews, others_reviews, and graph_data. Own reviews are style anchors. Others are content/item/community anchors.
  9. Fetch exact-item rating stats. fetch_item_rating_stats() aggregates all remaining reviews for the exact item. In eval, heldout_review_id is excluded so the hidden review is not leaked.
  10. Patch item metadata. Retrieved evidence may backfill item title/category/rating count, but request-provided title, price, description, and hints are applied last so user/eval inputs stay authoritative.
  11. Emit graph_data. Retrieved anchors are converted into lightweight graph nodes and edges for UI visualization before the LLM starts generating.
  12. Derive prompt signals. derive_signals() combines persona, own reviews, community reviews, and item metadata into a compact signal dictionary.
  13. Build prompts. The system prompt defines persona voice. The user prompt contains own-review style examples, community evidence, item metadata, category bias, and warnings. The rating prompt is built later after review text exists.
  14. LLM call 1 streams review text. call_review_stream() streams tokens from Gemini, Groq, or Cerebras.
  15. LLM call 2 predicts rating. call_calibrated_rating() asks the provider for JSON with rating, confidence, evidence_used, and calibration_reason.
  16. Deterministic rating calibration. _calibrate_rating() caps severe failures, bumps clean generous-user positives, blocks caveat-heavy positives, and adjusts using retrieved negative/neutral/community evidence.
  17. Fetch ground-truth references after generation. The code fetches exact item reviews only after generation so labels do not contaminate the prompt. Eval scoring uses the hidden SQLite holdout, not this late evidence.
  18. Emit final result. Final payload includes review text, predicted rating, locale, branch, anchor reviews, ground-truth references, rating evidence, item stats, and Pass 16 attribution flags.

Retrieval Details

Retrieval is not one query. It is a layered decision tree that tries to balance user style, item evidence, community evidence, and fallbacks.

Own Reviews: Style Anchors

ConditionQuery pathWhy it matters
No exact item, category known QUERY_A_SAME_CAT_BY_NAME Gets this user's reviews in the same product space.
No category match QUERY_OWN_RECENT Falls back to recent user voice/cadence.
Exact item known QUERY_A_SAME_CAT, then QUERY_A_ANY_CAT Finds same-category user history, then broader user history.
Any path QUERY_OWN_LOW_NEUTRAL supplement Adds examples of how this user writes when they are less satisfied.

Others Reviews: Content Anchors

Tier 1
Exact-item reviews

If item_id is known, the system fetches other users' reviews on that exact item. With PASS16_RATING_MIX=1, it slot-fills by rating buckets: one positive, one low, one neutral, then legacy fill. Verified purchase and helpful vote are tie-breakers inside each bucket.

Tier 2
Item-vector similar product reviews

The request/product metadata is converted to canonical item text, embedded with the configured sentence-transformer, and queried against db.index.vector.queryNodes('item_embedding', ...). Similar product reviews are filtered by category when available and reranked by item similarity, category match, price bucket match, locale, verified purchase, and helpful vote.

Tier 3
Category structural query

If category is known, QUERY_CATEGORY_REVIEWS pulls reviews from items whose category matches the target category, preferring same-locale reviews and recent reviews.

Tier 4
LLM-generated Cypher

If query text exists and structural retrieval is insufficient, the system asks the LLM to write a read-only Cypher query. The prompt includes schema rules, rating-mix requirements, category/brand scope, anti single-user dominance, and multi-item spread.

Tier 5
Review vector search

Last resort uses db.index.vector.queryNodes('review_embedding', 15, item_vec), filters by similarity > 0.72 and locale, then returns review anchors.

Prompt Blocks

System Prompt

Defines the role: write one authentic product review as the specific shopper. Includes locale, platform, tendency, vocabulary, emotional tone, target length, Pidgin/price notes, and Nigerian context when locale is NG.

User Prompt

Contains own past reviews, community reviews, exact-item caveats, extracted risks, product metadata, price, description, source item context, category bias, and retrieved rating mix.

Rating Prompt

Built after review generation. It includes the generated review, user rating profile, category mean, retrieved evidence, low/neutral evidence, exact-item distribution, and calibration rules.

Deterministic Rating Calibration

After the LLM returns a rating, _calibrate_rating() applies deterministic rules. These rules are important because the evaluation metric is numeric RMSE, and the LLM often anchors on 4 for positive reviews.

  • Severe failure terms cap the rating at 2.
  • Pass 16 generous bump can move 4 to 5 only for clean positive generated text with generous persona and low item risk.
  • Pass 16 ghost bump can move 4 to 5 on ghost items only when persona history is strong and low-variance.
  • Original rules bump generous caveat-free positives, prevent generous users from being pushed below 4 too easily, and lower ratings when negative terms or low community evidence appear.
  • Every final result stores a pass16_calibration trace in evaluation_context.

Scoring Calculations And Pass Results

The evaluation harness is designed to mirror the Task A judging rubric as closely as we can with local held-out labels. A real review is removed from Neo4j, the model predicts review text and a star rating, and the evaluator compares the prediction to the hidden SQLite copy of that review.

Per-Case Rating Error

For every held-out review case i, the evaluator has a hidden true user rating y_i and the model returns a predicted integer rating ŷ_i. 

error_i = ŷ_i - y_i
squared_error_i = (ŷ_i - y_i)^2
absolute_error_i = abs(ŷ_i - y_i)
Important implementation detail: evaluate_rubric() stores a per-case rmse_heldout_user using sqrt((ŷ_i - y_i)^2), which is numerically the same as absolute error for one case. RubricSummary then squares those per-case values again and computes the macro RMSE across the run. So the final run-level RMSE is the standard rating RMSE.

Run-Level Rating Metrics

MetricFormulaWhat it tells us
rmse_heldout_user sqrt(sum((ŷ_i - y_i)^2) / n) Main Task A rating accuracy metric. Lower is better. This is the number we optimize first.
mae_heldout_user sum(abs(ŷ_i - y_i)) / n Average star distance. Easier to interpret than RMSE, but it penalizes catastrophic misses less.
sum_sq sum((ŷ_i - y_i)^2) Useful for small fixed sets. On 15 cases, sum_sq=9 means sqrt(9/15)=0.7746.
rmse_proxy_mean sqrt(mean((ŷ_i - proxy_mean_i)^2)) Diagnostic only. Compares prediction to community/proxy review average, not the user's hidden rating.
rmse_persona_category sqrt(mean((ŷ_i - category_mean_i)^2)) Diagnostic only. Checks if ratings align with the user's train-only category bias.
rmse_persona_mean sqrt(mean((ŷ_i - persona_mean_i)^2)) Diagnostic only. Checks alignment with the user's overall train-only rating tendency.

Text Quality Metrics

MetricCalculationHow we use it
ROUGE-L Longest common subsequence F1 between predicted review and reference review. If rouge-score is installed, the evaluator uses rouge_scorer.RougeScorer(["rougeL"], use_stemmer=True). Secondary text quality signal. We track both max over references and mean across references.
Fallback ROUGE-L P = LCS / len(pred_tokens), R = LCS / len(ref_tokens), F1 = 2PR / (P + R) Used if rouge-score is unavailable.

Reference Selection During Eval

  1. Held-out user review: always the primary reference for eval holdout cases. Its text and rating come from eval_holdout_reviews.
  2. Proxy community reviews: exact-item ground-truth reviews fetched after generation. They can support ROUGE/proxy diagnostics but do not replace the hidden user label.
  3. Anchor reviews: retrieved prompt anchors used as fallback references in synthetic fixture mode when no better proxy exists.
  4. Persona/category targets: train-only persona stats loaded from eval_personas_train and eval_category_rating_bias_train when --persona-source eval_train is used.

Concrete Example: Pass 8 First-15 Score

Pass 8 on the first 15 fresh holdouts produced rmse_heldout_user = 0.7745966692. That corresponds to: 

n = 15
rmse = 0.7745966692
sum_sq = rmse^2 * n
sum_sq = 0.7745966692^2 * 15
sum_sq = 9

Interpretation:
- across 15 hidden reviews, total squared star error was 9
- this could be nine 1-star misses, or fewer larger misses
- lower sum_sq is better; one 3-star miss contributes 9 by itself

Why Pass 9 Is The Build-On Checkpoint

  • It keeps exact-item graph evidence as the first retrieval tier and adds item-vector retrieval for sparse/unknown products.
  • It removes the CatBoost branch after offline rescoring showed no improvement over the LLM/calibration path.
  • It has a 60-case Cerebras working estimate of about 0.9832 RMSE and 0.6667 MAE.
  • The remaining bottleneck is hidden low/medium ratings where visible public evidence is mostly positive.
  • The next work should improve negative/neutral evidence selection and calibration rather than adding another rating head.
Provider caution: Scores are only cleanly comparable when the same provider/model, review IDs, persona source, and delay/retry settings are used. Mixed-provider runs are useful diagnostics but weaker evidence for keeping or reverting code.

These are the places teammates can change the system with the clearest expected effects. The safest path is to change one layer at a time, run the same held-out review IDs, and compare rmse_heldout_user, catastrophic misses, and ROUGE-L.

Recommended Next Architecture: Item-Vector Hybrid

Keep the KG as the source of truth, then add item embeddings as a fallback/reranker. The strongest retrieval stack would be:

  1. Exact same-item reviews and full item rating distribution when available.
  2. Item-vector similar products inside the same or nearby category.
  3. Rerank similar products by price proximity, rating distribution, verified/helpful evidence, locale, and persona category affinity.
  4. Only then fall back to broad category or review-vector search.

This preserves what the graph is good at while fixing the broad-category weakness that hurts sparse items.

What To Monitor On Every Pass

  • rmse_heldout_user: main score.
  • Sum of squared rating errors on fixed review IDs: easiest pass-to-pass comparison.
  • Catastrophic misses: true <= 3 predicted >= 5, or true >= 5 predicted <= 3.
  • ROUGE-L max: text quality and content overlap.
  • Per-case retrieval branch and item stats: tells whether a pass actually changed the evidence.
  • Calibration trace: tells whether deterministic rules fired and whether they helped.
